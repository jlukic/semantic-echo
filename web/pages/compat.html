Safari and iOS

WebTransport on Safari is the holy grail, because datagrams are most useful where connections are lossy. Here are the common solutions to getting WebTransport working on iOS devices like iPads and iPhones.

What a server must advertise

RequirementIf absent
WT_MAX_SESSIONS ready never resolves and never rejects. Keep a client-side timeout or the page hangs forever.
WT_INITIAL_MAX_DATA, WT_INITIAL_MAX_STREAMS_UNI, WT_INITIAL_MAX_STREAMS_BIDI — required whenever WT_MAX_SESSIONS exceeds 1 Session refused before CONNECT. This conditional comes from draft-13; Safari enforces it and other engines do not.

There are still unknowns when working with Safari. The second and third rows on the endpoint board, :4440 and :4436, advertise byte-identical h3 SETTINGS and byte-identical QUIC transport parameters. Safari rejects one and accepts the other.

Whatever it is reacting to is not a value either side advertises, so no amount of auditing your own configuration will find it. Chrome and Firefox bind both.

Breaking Behaviors in Safari

BehaviorConsequence
Every WebTransportError carries an empty message Invalid settings, TLS rejection and wire-level refusal are indistinguishable from the client, all arriving about 50 ms after construction. Put your diagnostics server-side or you will not have any.
Datagram streams are createWritable() / createReadable() factories, not the writable / readable accessors Feature-detect both shapes. Code written against the specification alone reads undefined.
Flow-control credit is never released on FIN or RESET (319818) The connection deadlocks at 16 MB or 7,600 streams, whichever comes first. Long-lived sessions moving real volume will hit this.
User-installed root CAs are ignored for WebTransport TLS rejects with certificate_unknown even at full trust. A local CA that works for page loads fails here. Develop against hash pinning or real WebPKI, nothing between.
headers is unimplemented (311299) No request headers on the CONNECT. Carry what you need in the URL or the first message.
The wire implementation lives in Network.framework, not WebKit An OS point release can change SETTINGS handling with nothing appearing in Safari release notes. Re-test on every iOS and macOS update, not every Safari version.
The floor is iOS and macOS 26.4, not Safari 26.4 Gated on the OS version. An older OS running a newer Safari has no WebTransport at all. Support in WKWebView and in-app browsers is unconfirmed either way.

Using Certificates

serverCertificateHashes replaces certificate-chain validation rather than adding to it. The rules are narrow and mixing conventions fails silently.

RuleDetail
Hash the leaf DERSHA-256 over the leaf certificate only. Hashing the SPKI instead is the other convention in circulation, and it fails with no diagnostic.
Total validity ≤ 14 daysNot remaining validity, but the whole notBefore to notAfter span. A 90-day certificate cannot be pinned on any engine.
ECDSA P-256Required by Chrome, and RSA is excluded everywhere by the specification.
Algorithm string is "sha-256"Compared literally in WebKit. Any other casing never matches.
Incompatible with allowPoolingSafari throws NotSupportedError at construction if both are set.
Certificate names are irrelevantNothing checks SANs on this path. A localhost-SAN certificate serves a public origin fine.
Chrome ignores the system trust store for QUICmkcert and every other dev-certificate tool produce something Chrome will not accept for WebTransport. Pin instead.

These four endpoints share one echo handler and differ only in how the leaf is trusted.

Additional Gotchas

There is no HTTP/2 fallbackThe HTTP/2 binding is unimplemented in every browser. A client on a UDP-blocked path fails rather than falling back to TCP. Roughly 3 to 5 percent of clients cannot use QUIC at all, so ship a second transport at the application layer.
The draft is still movingChrome and Safari both still send the legacy :protocol = "webtransport" rather than draft-15's webtransport-h3. A server enforcing the newer token strictly rejects every current browser.
Baseline "newly available", not "widely available"Interoperable since 2026-03-24. The 30-month bar lands around September 2028.
